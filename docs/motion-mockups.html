Главное ограничение — и что из него следует

Прежде чем рисовать «как в iOS», нужно принять факт: меню приложения — это NSMenu, а не своё окно. Три места в коде уже наткнулись на это и записали вывод.

NSMenu не переразмечается, пока открыто

аккордеон невозможен
The session SET only changes on reopen (NSMenu can't add/remove rows reliably mid-track). Sources/Menu.swift:23

Значит, классического «раскрытия» — клик по серверу MCP, и под ним выезжают строки инструментов — в текущем каркасе не будет: высота окна меню фиксируется в момент открытия, и менять её на лету AppKit не даёт. Это не лень реализации, это граница NSMenu.

Но у приложения уже есть правильная поверхность для раскрытия — HoverCard из Sources/ToolCard.swift: отдельное borderless-окно уровня .popUpMenu, в котором показываются детали сессии и детали MCP-инструмента. Это настоящее NSWindow, а не строка меню, — там доступна вся Core Animation. Именно оно становится главной сценой: карточка не «появляется», а раскрывается из строки, под которой её вызвали.

Второй факт, который делает всю затею дешёвой, тоже уже записан в коде — и он про процессор:

Layer-hosted so the knob can slide on Apple's switch spring (CASpringAnimation), with the track color crossfading; CA animations run in the render server, so they play during menu tracking. Sources/MenuRows.swift:5

Core Animation отдаёт анимацию в WindowServer: процесс приложения делает работу один раз, при коммите, а дальше кадры интерполирует система. Поэтому вопрос «насколько это нагрузит процессор» имеет точный ответ — ровно настолько, сколько стоит один коммит транзакции, и ноль в покое. Дорого — только то, что перерисовывается каждый кадр на главном потоке, как нынешний SpinnerView с таймером на 20 Гц.

RS
Render server — бесплатно

CABasicAnimation / CASpringAnimation на opacity, transform, bounds, backgroundColor. Приложение не просыпается между кадрами. Сюда должно попасть всё новое.

C
Commit — разовая работа

Сборка и постановка анимаций при открытии меню или показе карточки. Десятки микросекунд на анимацию; бюджет — не больше 2 мс на одно открытие меню.

PF
Per-frame — запрещено

Timer + needsDisplay, NSWindow.setFrame(display:animate:), изменение размера NSVisualEffectView. Это главный поток каждый кадр. Ни одна новая анимация не должна попасть в этот класс.

Лесенка — только по запросу

Анимировать можно лишь строки со своим NSView. Обычные пункты (Open Claude, Настройки, Quit) рисует AppKit — они появляются сразу и не участвуют. В макете это видно: нижние три пункта стоят на месте, пока верхние выезжают. Так меню читается как подтормозившее, а не как оживлённое.

Плюс само окно меню macOS уже анимирует открытие — и переопределить это нельзя. Лесенка накладывается на системный переход поверх.

Внедрение

План по фазам

Порядок выбран так, чтобы каждая фаза была самостоятельной: любую можно остановить, и приложение остаётся связным.

Один файл с правилами движения

Motion.swift: длительности, кривые, готовые CASpringAnimation с параметрами из ToggleView, и главный вентиль — NSWorkspace.shared.accessibilityDisplayShouldReduceMotion плюс уровень из UserDefaults. Всё остальное спрашивает движение только у него. Ни одного нового Timer.

Договорённости

Правила, которые должны пережить рефакторинг

01
Ни одного нового таймера

Любая анимация — CAAnimation. Если жест нельзя выразить через слой, он не делается. Это и есть весь бюджет процессора.

02
Ноль работы при закрытом меню

Все анимации одноразовые, repeatCount никогда не бесконечный. Исключение одно — уже существующий спиннер проверки MCP.

03
Reduce Motion уважается всегда

При включённом системном флаге движение заменяется на кроссфейд, а не отключается насухо: пользователь всё равно должен видеть, что состояние сменилось.

04
Подсветка не догоняет курсор

Вход в подсветку строки — мгновенный. Анимируется только уход. Меню, где выделение отстаёт от мыши, ощущается сломанным, а не плавным.

05
Числа не врут по дороге

Пружина на шкале — без перелёта. 93% не имеют права на миг показать 98%: это те самые лимиты, ради которых приложение и существует.

06
Размер вибрант-слоя не анимируется

NSVisualEffectView с .behindWindow пересчитывает блюр на каждом кадре. Прозрачность — можно, геометрию — нет.

Как убедиться

Проверка вместо обещаний

Оценки выше — расчётные. Три измерения превращают их в факт, и их стоит снять до и после каждой фазы.

▸
Простой

sudo powermetrics --samplers tasks -n 5 -i 1000 с закрытым меню. Значение обязано совпасть с текущим до шума измерения.

▸
Открытие меню

Instruments → Time Profiler, тридцать открытий подряд. Смотреть суммарное время в menuNeedsUpdate: рост не больше 1.5 мс на открытие.

▸
Пропуск кадров

Instruments → Animation Hitches, наведение по списку из 20 строк MCP. Ноль hitch'ей; если они есть — почти наверняка это блюр карточки, лечится сокращением показа до 150 мс.

Макеты воспроизводят предложенные тайминги в браузере: длительности, задержки и кривые здесь те же, что уйдут в Swift. Пружина взята из настоящей CASpringAnimation приложения — mass 1, stiffness 260, damping 16 — и просчитана в точках, а не подобрана на глаз.
